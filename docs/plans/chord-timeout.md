# Design: a configurable wait for key prefixes in the desktop app, 5 s by default

> Status: proposed (2026-10-22), implementation not started.
> The ticket is [#0148](../tickets/0148-chord-timeout.md).
> Sylvain settled Decision 1 on 2026-10-22: the prefix waits 5 s by default.
> The plan proceeds on the recommendation of every other decision under "Decisions for the owner", so a worker can start at Unit 1 without waiting.
> Citations name a symbol and its file; line numbers are hints from 2026-10-22 and move with the code.
> Research: [chord timeout scouting](../../.agents/research/2026-10-22-chord-timeout-scouting.md), [prior art](../../.agents/research/2026-10-22-chord-timeout-and-account-picker-prior-art.md), [account picker scouting](../../.agents/research/2026-10-22-account-picker-scouting.md).

## Goal

Sylvain's report (2026-10-22): in the desktop app, after a prefix key such as `c` the which-key overlay "disappears after one or two seconds" and the chord is cancelled, so a late `a` archives the message instead of replying to all (`ca`).
He asks for the wait to be tunable in Settings and for a longer default.
The change is the desktop's; the TUI has no timeout and stays as it is.

## Current state

### Desktop

- `PREFIX_TIMEOUT_MS = 1200` is exported from `clients/desktop/src/keymap/useKeymap.ts` (around line 23); the prefixes are `PREFIXES` (`g`, `f`, `c`, `t`, `s`) plus Space.
- Inside `useKeymap`'s effect, `arm` (around line 199) stores `{ key, at }` in the `prefix` ref, publishes it with `setPendingPrefix` (`src/keymap/pendingPrefix.ts`) and starts one `setTimeout(disarm, PREFIX_TIMEOUT_MS)`.
- `take` (around line 207) disarms on every next key and returns the prefix only while `Date.now() - p.at < PREFIX_TIMEOUT_MS`.
- After the timer fires, nothing is pending, so `a` falls through to `MESSAGE_KEYS.a`, `archive`: this is the reported bug.
- Within the window any next key consumes the prefix: `onKey` calls `take()` first, and the `if (pending)` branch calls `handled()` and runs `resolvePrefix`, which for an unbound combo returns `"notice"` in Mail (and `describeKey` finds nothing for `"cEscape"`) or null in a view.
- Escape therefore already cancels a pending prefix and is swallowed: it does not also clear the selection or leave the search.
- Leaving the window (`onBlur`, around line 440) and moving the focus into a field or the embedded editor (`onFocusIn`) disarm; a mouse click does not.
- The which-key popup, `PrefixPopup` (`src/components/palette/PrefixPopup.tsx`), has no timer of its own: it shows while `usePendingPrefix()` is non-null, no dialog is open, the shell is up and no field has the focus, so the one timer both cancels the chord and hides the popup.
- `ActivityLogDialog` (`src/components/activity/ActivityLogDialog.tsx`, around lines 7 and 83) imports `PREFIX_TIMEOUT_MS` for its own `gg`, a double `g` inside the dialog with no popup.
- `prefixPopup.test.tsx` (`src/components/palette/`, around lines 109 to 127) pins the 1200 ms expiry with fake timers at `PREFIX_TIMEOUT_MS - 1` and `+ 1`.
- `useKeymap(state, dispatch)` keeps `ref.current = state` on every render, so a value in `AppState` is readable from the key handler without re-running the effect; the effect depends on `[dispatch]` only.

### Where desktop settings live

- `Prefs` (`src/app/state.ts`, around line 141: `sidebarCollapsed`, `listWidth`, `activityHidden`, `flatListAccounts`) is `state.prefs`, loaded once by `loadPrefs` (`src/app/prefs.ts`) into `initialState` and saved by an effect in `src/app/store.tsx` on every change, under the localStorage key `mailypoppins.desktop.prefs.v1`.
- `loadPrefs` validates each field and falls back to its default, clamping `listWidth` between `LIST_WIDTH_MIN` and `LIST_WIDTH_MAX`.
- `desktop.json` in the app config directory holds the other desktop choices as string values per `SettingKey` (`clients/desktop/src-tauri/src/settings.rs`: `editor`, `theme`, `reader_mode`, `editor_colors`), read and written through the Tauri commands `setting_get` and `setting_set`; its TypeScript `SettingKey` type is generated by ts-rs (`pnpm gen:types`, which runs `cargo test` in `src-tauri` and needs the Mac).
- `config.toml` is the daemon's file, served by `config.get` (`src/daemon/config.rs`); `email.send_hold_secs` (`crates/mp-core/src/config.rs`) is the numeric precedent, and the Settings view shows it read-only.

### The Settings view has editable controls

The chord scouting note says Settings is read-only; that is out of date.
`SettingsView` (`src/components/settings/SettingsView.tsx`) has five controls today:

- `ThemeField` and `ReaderModeField`: button groups with the current choice `aria-pressed`, stored in `desktop.json`.
- `EditorSettingField`: a text field with Save, through `editor_setting_get|set`.
- `EditorColorsField`: a button group, stored in `desktop.json`.
- `ConversationViewSwitch` on each account card: a switch stored in `Prefs` (`flatListAccounts`), the precedent for a Settings control backed by localStorage.

Only the daemon's own settings (`config.toml`) are read-only there, with "Open config.toml" and Reload.

### TUI

- `pending_prefix: Option<char>` on `App` (`clients/tui/src/app/mod.rs`, around line 69) has no timer: a prefix waits until the next key.
- `resolve` (`clients/tui/src/app/keymap.rs`, around line 1667) runs in strict prefix mode: while a prefix is pending only that family's continuations match, so Esc or any other non-continuation clears the chord at the end of `App::handle_key` ("No live binding matched", `keys.rs`, around line 147) and fires nothing.
- The which-key popup (`render_prefix_popup`, `clients/tui/src/ui/mod.rs`) shows for as long as the prefix is pending.
- The TUI has its own presentation file, `tui.json` beside `config.toml` (`clients/tui/src/prefs.rs`), and no `[tui]` table in `config.toml`.

## Design

- A new `Prefs` field `prefixWaitMs: number | null`, where null means the prefix waits for the next key; the allowed values are `PREFIX_WAITS = [null, 5000, 3000, 1500]` in `state.ts`, and `DEFAULT_PREFS.prefixWaitMs` is 5000 (Decisions 1 to 3).
- `loadPrefs` accepts only a value from `PREFIX_WAITS` and keeps the default for a missing or unknown one, so an old saved object and a hand-edited one both load.
- A reducer action `prefix_wait_set { ms }` replaces the field; the existing `store.tsx` effect saves it.
- In `useKeymap`, `arm` reads `ref.current.prefs.prefixWaitMs` and starts the timer only for a number; `take` applies the age check only for a number; `PREFIX_TIMEOUT_MS` goes.
- A `pointerdown` listener on the window disarms a pending prefix, beside `blur` and `focusin`, so a click elsewhere never leaves a chord armed for a later key; the popup is `pointer-events-none`, so it never receives the click itself.
- Escape keeps its current behaviour, cancel and swallow, now pinned by a test (Decision 4).
- The popup keeps following the pending prefix exactly, so it stays as long as the chord is pending, 5 s by default, and closes with it; it still appears at once, with no show delay (Decision 6).
- `ActivityLogDialog` keeps a fixed local `GG_WINDOW_MS = 1200` for its own `gg`: no popup shows a pending `g` inside that dialog, so an invisible prefix must lapse on its own.
- Settings gains a "Prefix keys" row in its General section, after Editor colours: a button group in the style of `ReaderModeField` with "Wait for the next key", "5 s", "3 s" and "1.5 s", the current one `aria-pressed`, and the hint "After g, f, c, t, s or Space, how long the key list waits for the second key; Escape cancels it."
- No palette entry and no keyboard binding for the setting: it is set once.
- The TUI does not change (Decision 5).

## Decisions for the owner

### 1. The default wait

Decided by Sylvain on 2026-10-22 (decision log, same date): the prefix waits 5 s by default for its second key.
"Wait for the next key" remains a choice in Settings, beside 3 s and 1.5 s.
Today's 1.2 s is the reported bug: a second key pressed after the timer runs its flat action, `a` archiving where `ca` was meant.
5 s leaves room for a slow second key, and an accidental prefix still lapses on its own.
No timeout by default was rejected because an accidental prefix would keep the popup up until Escape.
Waiting for the next key is what the TUI, Emacs, Helix and Zed do (prior-art note, findings 2, 3 and 5), and the Settings choice keeps it available.
3 s was rejected as leaving less room for the second key.

### 2. Preset values or a free number

A button group with four presets ("Wait for the next key", 5 s, 3 s, 1.5 s) matches the Theme, Reader and Editor colours rows, needs no input validation and cannot be set to a value that breaks typing.
A numeric field allows any value but brings a validation message, a clamp range and a Save button for a setting changed once.
Recommendation: the four presets, with 5 s pressed by default; today's 1.2 s is left out on purpose, since a shorter wait is what the report is about.

### 3. Where the setting is stored

Option one is `Prefs` in localStorage: `useKeymap` reads it synchronously from `state.prefs`, the whole change is TypeScript that `pnpm test` covers on either machine, and the account card's Conversation view switch is already a Settings control stored there; it is lost if the webview's storage is cleared, and it cannot be edited by hand.
Option two is a `desktop.json` key through `setting_get|set`, the home of the Theme, Reader and Editor colours rows; it survives a storage reset and is readable on disk, but it needs a new `SettingKey` variant and its `check` in `src-tauri/src/settings.rs`, a regenerated `SettingKey.ts` (`pnpm gen:types`, Mac only), the fixture backend's key (`src/fixture/backend.ts`), and an asynchronous load during which the default applies.
Option three is a `config.toml` key served through `config.get`; it would configure a timeout the TUI does not have, a client does not write `config.toml` (the rule stated in `clients/tui/src/prefs.rs`), and the Settings view shows `config.toml` read-only.
Recommendation: option one, `Prefs`; moving it to `desktop.json` later is a contained change if the storage reset ever bites.

### 4. Escape while a prefix is pending

Escape already cancels the prefix and is swallowed in both clients, so `c` then Escape neither replies nor clears the selection.
The alternative, cancelling and then running Escape's own action, would make one Escape do two things, and the user pressed it to back out of the chord.
Recommendation: keep cancel-and-swallow and pin it with a test in the desktop; the TUI's strict prefix mode already guarantees it.

### 5. The TUI

The TUI never times out a prefix and has no report against it.
Adding a timer there would add the desktop's bug to the TUI.
Recommendation: no TUI change.

### 6. A delay before the popup appears

The prior-art note recommends a short delay (about 300 ms) before the popup shows, so a fast typist never sees it flash, kept separate from the wait.
The report is about the popup leaving too early, not appearing too early, and the TUI shows its popup at once too.
Recommendation: no show delay in this ticket; it can be a later setting if the flash bothers anyone.

## Acceptance criteria

- In the desktop app the prefix wait is configurable and defaults to 5 s.
- With the default, `c`, a pause of 4 s, then `a` replies to all.
- With the default, after `c` and 5 s without a key, the popup closes and the prefix lapses, so a later `a` archives.
- Settings has a "Prefix keys" row with "Wait for the next key", 5 s, 3 s and 1.5 s, with 5 s pressed by default; the choice applies to the next prefix without a restart and survives a restart.
- With "Wait for the next key", the popup stays until the second key, and `c`, a pause of any length, then `a` replies to all.
- With a timed choice, the popup and the pending prefix end together when the time is up.
- Escape over a pending prefix cancels it and does nothing else; a click anywhere cancels it.
- The activity log's `gg` behaves as today.
- The TUI is unchanged.
- `pnpm test` and `pnpm build` pass.

## Risks

- With "Wait for the next key" chosen, a stray prefix stays armed until the next key; the popup makes this visible, and Escape, a click, leaving the window and focusing a field all clear it.
- A test elsewhere may rely on the 1.2 s lapse indirectly, for example by typing a prefix and later a flat key after advancing fake timers by less than 5 s; the worker runs the whole suite after Unit 1 and fixes such a test by pressing Escape or by advancing past 5 s.
- The `pointerdown` listener must not disarm for a click inside the embedded editor's terminal or the reader frame in a way that loses a key; a click there already moves the focus, which `focusin` handles, so the listener only adds the case of a click on a non-focusable area.
- `loadPrefs` returns `DEFAULT_PREFS` as a whole when parsing fails, so a broken stored object resets the wait with the other preferences, as it already does for the pane sizes.
